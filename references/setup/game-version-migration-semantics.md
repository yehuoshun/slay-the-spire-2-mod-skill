# 跟随游戏版本升级 · 非签名断点（编译能过，行为变了）

> 与 [`game-version-migration.md`](./game-version-migration.md) 配套：那份讲**编译就报错**的签名断点，这份讲**编译全绿但行为变了**的语义断点。来源：0.111→0.113 的原生卡实现逐卡对账（482 条精确 recipe，45 个池卡实现有变化，其中大多数只是把命中数暴露成原生变量 —— 正说明这类断点靠读 diff 才能发现，编译器和 `CS0115` 帮不上忙）。

## 一、语义断点清单

| 断点 | 0.113 的实际行为 | 跟着改什么 |
|---|---|---|
| 多段伤害的身份 | 原生多段升级绑到 `HitCount`，而 `Repeat` 另有用途（Refract 的玻璃生成、Bouncing Flask 的中毒层数）；`CalculatedHits` 的原生类型变成 `CalculatedHitCountVar`，但**身份要沿用原 ID** | 别用「伤害 × 次数」的数字字面量去匹配卡；也别把命中次数和重复次数合成一个变量 |
| 升级审计的对象 | 升级记录的是**数值槽 + 它的来源变量绑定**，含 `HitCount - 1` 这类变换 | 只校验「能否构造出升级计划」会漏判；要校验 applied numeric slots 对得上 source binding |
| 零 delta 的升级 | `UpgradeDelta = 0` 合法（Speedster 3 点伤害只升级 Innate 关键词），纯标记升级（FTL 打出次数 3→4）也合法 | 别把「数值没变」当成数据缺失；也别让只升级关键词的绑定掩盖了陈旧的 base 数值 |
| 升级之外的关键词增删 | v113 会记录 non-upgrade 的 keyword add/remove。重放生成升级时若重建缓存，升级专用的 Innate 会被误判成「外部添加的关键词」 | 重放升级时保留原生的 upgrade scope，只把真正的外部变更叠上去 |
| 降级（downgrade） | 原生 downgrade 会**克隆 canonical slot 的变量与费用** | 逐实例定义要在被降级的回调里（`AfterDowngraded`）、且在原生附魔/affliction 重新应用**之前**重建自己的基态；否则被改过/重平衡过的卡会继承规范槽的值 |
| 战斗内选择 | 原生随机选牌从 Shuffle 迁到 `CombatCardSelection`；选择可被 owner 死亡或战斗终止取消，并新增 `CombatId` | 选择要捕获所属战斗与 `CombatId`，异步结果回来先判过期，再完成强制选择；自动选堆要按原生 v113 的排序，等待后再校验牌堆仍活着 |
| 击杀来源 | 击杀命令现在带 source card，死亡钩子也加了 source 参数 | 生成效果击杀 Osty/敌人时要传原生来源身份，否则和原生事件流对不上 |
| 复制伤害 | Omnislice 走原生 capped damage 传播 | 对复制出来的伤害不要再套一遍伤害修饰符 |
| 直改立绘 | `SetPortraitTexture` 会刷新原生缓存的 atlas UV/blur | 绕过它直接换纹理会花屏/糊边；只在最终纹理/表现真变了时才调用 |

## 二、池与槽位只许追加

给原生池加卡只能把新槽位**追加在尾部**（Colorless 52→53），旧槽位身份和稀有度位置一个都不能动；旧存档用**选择性恢复**只补新槽，已有卡定义保留它持久化的 operation spec，不要整体重建。同理，上游某张源卡改了效果，**不要因此下调共享组件的出现概率**（对应组件只是失去该来源的「原生存在」先验），旧存档里的旧效果也不重写。

## 三、怎么验证这类改动

- **对账脚本**：逐卡导出 base 与首升级之后的费用、变量绑定、关键��，跨版本 diff，别靠人读反编译。
- **真引擎回归**：在隔离 Godot 进程里加载真原生卡，比 base/首升级的费用、变量、关键词，再把中英双语描述都格式化一遍（实测一次跑 1146 个语言/卡用例 + 2212 条描述）。
- **只比指纹不够**：读档往返后哈希一致，仍可能白跑了一次兼容生成（慢，且可能改写派生身份）。加一条「Continue 期间禁止任何池生成」的硬断言，比只比指纹更结实。
- **隔离档**：回归一律用隔离 profile/fixture，不读也不改用户存档；测试结束关掉测试清单，再核对产出的 dll 哈希与发布包一致。

## 常见问题

**Q：升级测试过了，为什么读旧档后卡的效果变成了「另一张卡」的描述？**
A：多半是复用注册表模板时只按本地化 ID 命中，没校验该 ID 当前的 operation opcode/variant。复用前先校验，旧存档要保留它自己持久化的效果规格，而不是借用改写后组件的描述。

**Q：为什么改了共享组件的一个来源卡，生成出来的卡强度就整体掉了？**
A：源卡改写后，对应组件只是「不再有原生存在先验」；把概率一起下调等于双重惩罚。正确做法是该组件的旧实例照旧可读可执行，新生成只按剩余来源的先验走。
